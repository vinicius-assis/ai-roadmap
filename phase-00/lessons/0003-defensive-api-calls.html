Fase 0 · Lição 3 · ~30 min

Chamadas de API que não quebram em produção

Timeout com AbortController, retry com backoff + jitter, e o 429.

APIs de LLM falham o tempo todo de formas temporárias: a rede engasga, o provedor devolve 529 Overloaded, ou você bate no rate limit e leva um 429. Nenhuma dessas é motivo pra derrubar seu programa — quase sempre a mesma requisição funciona se você esperar um pouco e tentar de novo. Esta lição é o padrão que você vai copiar pra dentro de todo projeto do roadmap.

1. Timeout: uma requisição não pode esperar pra sempre

fetch não tem timeout embutido. Se o servidor simplesmente não responde, sua Promise fica pendente indefinidamente. A solução é o AbortController: um objeto com um signal que você passa pro fetch e um .abort() que cancela a requisição. 

async function fetchComTimeout(url: string, ms: number): Promise<Response> {
  const ac = new AbortController();
  const timer = setTimeout(() => ac.abort(), ms);
  try {
    return await fetch(url, { signal: ac.signal });
  } finally {
    clearTimeout(timer);   // sempre limpa, deu certo ou não
  }
}

Quando .abort() dispara, o fetch rejeita com um erro de nome "AbortError". O clearTimeout no finally evita deixar um timer pendurado quando a resposta chega antes do prazo. (MDN: AbortController)

Por que o clearTimeout precisa estar no bloco finally?

C. Se a resposta chega em 300ms mas o timeout era 5000ms, aquele setTimeout ainda está agendado. Sem clearTimeout ele dispara depois, chamando abort() à toa e mantendo o processo vivo por mais tempo. O finally garante a limpeza nos dois caminhos — sucesso e erro.

2. Retry: tente de novo, mas com paciência crescente

Falha temporária → espere → tente de novo. O truque é quanto esperar. Repetir na hora, várias vezes, só piora um servidor já sobrecarregado (todo mundo batendo ao mesmo tempo). A resposta é backoff exponencial: dobre a espera a cada tentativa. 

tentativa 1 falhou → espera ~1s
tentativa 2 falhou → espera ~2s
tentativa 3 falhou → espera ~4s
tentativa 4 falhou → desiste, propaga o erro

Jitter: um tempero aleatório

Se 1000 clientes falham no mesmo segundo e todos esperam exatamente 1s, eles voltam exatamente juntos — e derrubam o servidor de novo (o "thundering herd"). Adicione um jitter: uma fração aleatória em cima da espera, pra espalhar as tentativas no tempo. 

const base = 1000 * 2 ** tentativa;      // 1000, 2000, 4000...
const espera = base + Math.random() * base; // + 0 a 100% aleatório
await new Promise((r) => setTimeout(r, espera));
"Retry com backoff exponencial e jitter é o padrão de fato para lidar com sobrecarga." — Google SRE Book, Handling Overload

3. Nem todo erro merece retry

Antes de repetir, olhe o que falhou:

Situação Retry?
429 Too Many RequestsSim — respeitando o header Retry-After
500 / 502 / 503 / 529, erro de rede, timeoutSim — backoff + jitter
400 Bad Request, 401, 404, 422Não — seu pedido está errado, repetir não muda nada
429 e o header Retry-After: quando o provedor te limita, a resposta muitas vezes traz Retry-After: 12 (segundos) ou uma data. Isso é o servidor te dizendo exatamente quanto esperar — obedeça em vez de chutar com o backoff. const s = res.headers.get("retry-after").

4. O padrão completo, montado

async function chamarComRetry(
  url: string,
  opts: RequestInit = {},
  maxTentativas = 4,
): Promise<Response> {
  for (let tentativa = 0; tentativa < maxTentativas; tentativa++) {
    try {
      const res = await fetchComTimeout(url, 10_000);

      if (res.ok) return res;                       // 2xx — pronto
      if (res.status < 500 && res.status !== 429)   // 4xx "culpa sua"
        throw new Error(`erro permanente: ${res.status}`);

      // 429 ou 5xx — cai pro retry abaixo
      const retryAfter = Number(res.headers.get("retry-after")) || 0;
      await esperar(retryAfter * 1000 || backoff(tentativa));
    } catch (err) {
      if ((err as Error).name !== "AbortError" && !ehTemporario(err)) throw err;
      if (tentativa === maxTentativas - 1) throw err;  // última: desiste
      await esperar(backoff(tentativa));
    }
  }
  throw new Error("esgotou as tentativas");
}

Você não precisa decorar isto — precisa reconhecer as peças: loop de tentativas, classificar o erro, esperar com backoff/jitter ou Retry-After, desistir na última. Bibliotecas como p-retry empacotam isso, mas os SDKs oficiais da OpenAI e Anthropic já fazem retry sozinhos — o valor aqui é entender o que eles estão fazendo por baixo.

Chega um 400 Bad Request. Qual a acao correta?

B. 400 significa que o servidor entendeu o pedido e ele está errado — JSON inválido, parâmetro faltando. Mandar de novo, igual, dá 400 de novo. Só 429 e 5xx (mais rede/timeout) merecem retry.

Prática (20 min)

Objetivo: escrever chamarComRetry contra um servidor falso que falha as primeiras vezes e depois responde, e ver o backoff no log.

  1. Servidor falso. let chamadas = 0. Função async function apiFalsa(): Promise<{ status: number }> que faz chamadas++ e retorna { status: 503 } nas 2 primeiras chamadas, { status: 200 } da 3ª em diante.
  2. backoff. function backoff(tentativa: number): number → const base = 100 * 2 ** tentativa (100, 200, 400… — ms curtos pra testar rápido), retorne base + Math.random() * base.
  3. Loop de retry. async function chamarComRetry(maxTentativas = 5). Em cada volta: chame apiFalsa(); se status === 200, imprima "ok na tentativa", tentativa e return; senão imprima "tentativa", tentativa, "falhou (", status, ") esperando", ms e await o backoff. Se estourar maxTentativas, throw new Error("esgotou").
  4. Caso permanente. Mude apiFalsa pra retornar { status: 400 } sempre. No loop, trate: se status for >= 400 && < 500 && !== 429, throw na hora sem retry. Chame dentro de um try/catch e imprima a mensagem.

Saída esperada (aproximada)

# passos 1-3:
tentativa 0 falhou ( 503 ) esperando 143 ms
tentativa 1 falhou ( 503 ) esperando 271 ms
ok na tentativa 2

# passo 4 (status 400 sempre):
erro permanente, sem retry: 400

Os ms do backoff variam (100–200, 200–400…) por causa do jitter — a ordem de grandeza é o que importa.
