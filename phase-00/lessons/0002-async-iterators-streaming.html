Consumindo um stream de tokens

Iteradores assíncronos, for await...of e async generators.

Quando você chama um LLM com stream: true, a resposta não chega de uma vez — chega em pedacinhos (chunks), um token ou poucos tokens por vez, ao longo de vários segundos. É isso que faz o texto "aparecer digitando" no ChatGPT/Claude. Do lado do código, esse stream é um iterável assíncrono, e a ferramenta pra consumir é o for await...of. Sem isso você fica preso a esperar a resposta inteira.

1. Lembra do for...of? Agora com await

for...of percorre uma coleção que já está inteira na memória (um array, um Set). for await...of percorre uma fonte que produz valores ao longo do tempo — e pausa a cada volta até o próximo valor chegar. 

// síncrono: todos os itens já existem
for (const n of [1, 2, 3]) {
  console.log(n);
}

// assíncrono: cada item chega quando chega
for await (const chunk of stream) {
  process.stdout.write(chunk);   // imprime conforme recebe
}

Cada iteração do for await...of faz um await implícito no "próximo item". O loop só continua quando esse item resolve. Fim do stream = fim do loop. (MDN: for await...of)

2. Do outro lado: async generators produzem o stream

Uma função geradora assíncrona — async function* — é a forma mais simples de criar um iterável assíncrono. Cada yield entrega um valor pra quem está consumindo; a função pausa ali até pedirem o próximo. 

async function* gerarPedacos(): AsyncGenerator<string> {
  const palavras = ["Oi", " ", "mundo", "!"];
  for (const p of palavras) {
    await new Promise((r) => setTimeout(r, 300)); // simula latência da rede
    yield p;                                       // entrega um chunk
  }
}

for await (const pedaco of gerarPedacos()) {
  process.stdout.write(pedaco);   // "Oi" ... " " ... "mundo" ... "!"
}
// texto aparece aos poucos, ~300ms entre cada pedaço
Isto é praticamente a API real. O SDK da Anthropic devolve exatamente uma coisa dessas: const stream = await client.messages.create({ stream: true, ... }) e depois for await (const event of stream). Os event são objetos com um tipo (content_block_delta etc.) e o texto fica em event.delta.text.

O que o for await...of faz ao chegar no fim de cada volta do loop?

B. Cada iteração dá um await implícito no próximo item. O corpo do loop só roda de novo quando esse item chega. Por isso o for await...of é a ferramenta certa pra stream: ele consome no ritmo em que os dados aparecem, sem bufferizar tudo antes.

3. O ganho concreto: primeira palavra na tela quase na hora

Sem stream, o usuário olha pra uma tela parada até a resposta inteira ficar pronta — pode ser 10, 20 segundos. Com stream, a primeira palavra aparece em ~500ms e o resto vai chegando. A latência total é a mesma, mas a latência percebida despenca. Para produto, isso é decisivo. 

// sem stream — bloqueia até o fim
const msg = await client.messages.create({ /* ... */ });
console.log(msg.content[0].text);   // tudo de uma vez, depois de 12s

// com stream — mostra conforme gera
const stream = await client.messages.create({ stream: true, /* ... */ });
let completo = "";
for await (const event of stream) {
  if (event.type === "content_block_delta") {
    completo += event.delta.text;
    process.stdout.write(event.delta.text);   // aparece token a token
  }
}

4. Acumular enquanto faz stream

Padrão que você vai repetir muito: mostrar cada pedaço e montar a string completa pra usar depois (salvar no banco, logar, devolver numa API). Um let completo = "" fora do loop, completo += pedaco dentro. Simples assim.

5. Erro no meio do stream

A conexão pode cair na terceira palavra de vinte. Um for await...of propaga esse erro como throw — então a mesma regra da Lição 1 vale: envolva com try/catch se precisar tratar. O que você já acumulou em completo continua lá; decida se aproveita o parcial ou descarta. 

let completo = "";
try {
  for await (const pedaco of gerarPedacos()) {
    completo += pedaco;
  }
} catch (err) {
  console.error("stream caiu; tinha até aqui:", completo);
}

Por que fazer stream se a latencia total ate a resposta completa nao muda?

A. O total de tempo até o último token é praticamente igual. O que muda é que a primeira palavra aparece em centenas de milissegundos em vez de dezenas de segundos — a espera sentida some. Custo por token e qualidade da resposta não têm relação com streaming.

Sua vitória de hoje

  • consumir qualquer iterável assíncrono com for await...of;
  • criar um você mesmo com async function* e yield;
  • acumular a resposta completa enquanto faz stream, e tratar erro no meio.

Prática (15 min)

Objetivo: simular um stream de LLM e consumi-lo token a token, medindo quando o primeiro token chega vs quando o último chega.

  1. Crie o gerador. async function* stream(texto: string): AsyncGenerator<string>. Quebre texto em palavras (texto.split(" ")). Para cada palavra: await 200 ms, depois yield a palavra + " ".
  2. Consuma com timing. const t0 = Date.now(). Num for await...of sobre stream("o rato roeu a roupa do rei"): no primeiro pedaço, imprima "primeiro token:", Date.now() - t0; a cada pedaço, process.stdout.write(pedaco); acumule em let completo = "".
  3. Depois do loop: imprima "ultimo token:", Date.now() - t0 e completo.trim().
  4. Erro no meio. Faça o gerador dar throw new Error("conexao caiu") ao chegar na 4ª palavra. Envolva o consumo em try/catch e, no catch, imprima o que tinha acumulado até então.

Saída esperada (aproximada)

primeiro token: 201
o rato roeu conexao caiu; acumulado ate aqui: "o rato roeu "

(Sem o throw do passo 4, você veria as 7 palavras e ultimo token: ~1400.) Os milissegundos variam alguns pontos — o que importa é primeiro token perto de 200 e não de 1400.
