O que o await realmente faz

Um modelo mental para async/await, e o tratamento de erro que vem junto.

Toda chamada a um SDK de LLM é assíncrona. const res = await client.messages.create(…) envia uma requisição HTTP e o modelo leva segundos para responder. Se você não tem uma imagem nítida do que o seu programa faz durante esses segundos, streaming, retries, tratamento de rate limit e chamadas paralelas vão todos parecer mágica impossível de depurar. Esta lição constrói essa imagem.

1. Uma Promise é uma caixa que vai conter um valor depois

Quando você chama algo assíncrono — fetch(url), um método de SDK — você não recebe o resultado. Você recebe uma Promise: um objeto que agora está pendente (pending) e depois vai resolver (fulfill) com um valor ou rejeitar (reject) com um erro. 

const p = fetch("https://api.exemplo.com/models");
console.log(p); // Promise { <pending> }  — os dados NÃO estão aqui ainda

2. await abre a caixa — e pausa esta função

await p faz duas coisas: suspende a função async atual até p se resolver, e então retorna o valor resolvido (ou lança a rejeição como erro). O ponto crucial: só esta função pausa. O resto do programa — o event loop — continua rodando. 

async function listarModelos() {
  console.log("A: prestes a dar await");
  const res = await fetch("https://api.exemplo.com/models"); // suspende aqui
  console.log("C: resposta chegou");                         // retoma aqui depois
  return res.json();
}

console.log("1: antes da chamada");
listarModelos();
console.log("2: depois da chamada");   // roda ANTES de "C" — listarModelos está estacionada

// Ordem da saída: 1  →  A  →  2  →  C

"2" aparece antes de "C" porque chamar uma função async a executa de forma síncrona até o primeiro await, e então devolve o controle. A continuação depois do await fica na fila para quando a Promise resolver. (MDN: await)

No código acima, qual é a ordem correta da saída?

B. listarModelos() roda de forma síncrona até o await, então "1" e depois "A" aparecem. Aí ela suspende e o controle volta para quem chamou, então "2" aparece. "C" só roda depois que a Promise do fetch resolve, num tick posterior do event loop.

3. async/await É Promise — só que legível

Estas duas funções são equivalentes. async/await é açúcar sintático sobre a mesma máquina.

// Cadeia de Promise
function obterResposta() {
  return client.messages.create({ /* ... */ })
    .then(msg => msg.content[0].text)
    .then(text => text.trim());
}

// async/await
async function obterResposta() {
  const msg = await client.messages.create({ /* ... */ });
  const text = msg.content[0].text;
  return text.trim();
}

Uma função async sempre retorna uma Promise. return text.trim() resolve essa Promise; um throw a rejeita.

4. Tratamento de erro: .catch() vira try/catch

Uma Promise rejeitada que você deu await lança uma exceção de verdade naquela linha. Envolva. 

async function obterResposta() {
  try {
    const msg = await client.messages.create({ /* ... */ });
    return msg.content[0].text.trim();
  } catch (err) {
    // falha de rede, rate limit 429, 500 da API — tudo cai aqui
    console.error("chamada ao modelo falhou:", err);
    throw err; // ou retorne um fallback
  }
}
Armadilha: um erro dentro de uma função async que ninguém deu await nem .catch() vira uma unhandled promise rejection — não quebra no ponto da chamada e é fácil de não perceber. Sempre tenha um try/catch ou um .catch() em algum ponto da cadeia.

5. Sequencial vs paralelo — o erro que dobra sua latência

// LENTO: 2 segundos — a segunda chamada espera a primeira
const a = await modelo.perguntar("resuma o doc A");
const b = await modelo.perguntar("resuma o doc B");

// RÁPIDO: ~1 segundo — as duas requisições ao mesmo tempo
const [a, b] = await Promise.all([
  modelo.perguntar("resuma o doc A"),
  modelo.perguntar("resuma o doc B"),
]);

Use await dentro de um loop só quando cada passo realmente depende do anterior. Chamadas independentes vão para Promise.all.

Quando dar await em chamadas uma após a outra em vez de Promise.all?

C. await sequencial é correto quando há dependência real de dados (chamada 2 precisa da saída da chamada 1). Fora disso, você só serializa trabalho que poderia acontecer em paralelo, adicionando latência à toa. Rate limit se resolve com backoff (Lição 3), não deixando tudo sequencial.

Sua vitória de hoje

Você agora consegue:

  • prever a ordem de execução em volta de um await;
  • converter uma cadeia .then() para async/await com try/catch;
  • identificar quando usar Promise.all em vez de awaits sequenciais.

Prática (10 min, faça num arquivo de verdade)

Objetivo do exercício inteiro: ver com seus próprios olhos que 3 await em sequência levam ~3×500 ms, enquanto Promise.all leva ~1×500 ms. A função dobrarDevagar é só uma "operação lenta" de mentira, fingindo ser uma chamada de API.

  1. Construa a função lenta. async function dobrarDevagar(n: number): Promise<number>. Dentro dela, na ordem:
    1. uma linha que só pausa por 500 ms — await new Promise(r => setTimeout(r, 500)), sozinha, sem return;
    2. depois, return n * 2.
  2. Meça o sequencial. const inicio = Date.now(), depois await dobrarDevagar(...) três vezes, uma linha após a outra. No fim, console.log(Date.now() - inicio). Espere ~1500 ms.
  3. Meça o paralelo. Novo inicio. Rode as três chamadas com await Promise.all([ ... ]) (um await só, uma lista com as 3 chamadas). Imprima o tempo. Espere ~500 ms.
  4. Trate um erro. Faça dobrarDevagar dar throw new Error("boom") quando n < 0. Chame com -1 dentro de um try/catch para o programa imprimir uma mensagem em vez de quebrar.

Rode com npx tsx practice.ts (ou node se compilar). Me mande o arquivo de volta que eu reviso.
