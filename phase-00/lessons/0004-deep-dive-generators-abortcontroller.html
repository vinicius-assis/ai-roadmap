Aprofundando: generators e AbortController

Como as duas peças funcionam por dentro — e onde você vai usar de verdade.

Nas Lições 2 e 3 você usou generators e AbortController pra resolver um problema. Aqui a gente abre a caixa: o protocolo de iteração, o yield nos dois sentidos, um controller controlando várias operações de uma vez, e os helpers modernos (AbortSignal.timeout, AbortSignal.any). É a diferença entre copiar o padrão e saber ajustá-lo.

Parte A — Generator functions

A1. Comece pelo generator síncrono

Antes de async function*, entenda function*. Um generator é uma função que pausa e retoma. Chamar ela não roda o corpo — devolve um iterador. O corpo só anda quando você chama .next(). 

function* contador() {
  console.log("comecou");
  yield 1;
  console.log("entre 1 e 2");
  yield 2;
  return 99;          // vira { value: 99, done: true }
}

const it = contador();          // nada impresso ainda — só criou o iterador
console.log(it.next());         // "comecou"  → { value: 1, done: false }
console.log(it.next());         // "entre 1 e 2" → { value: 2, done: false }
console.log(it.next());         // { value: 99, done: true }
console.log(it.next());         // { value: undefined, done: true }

Cada .next() roda o corpo até o próximo yield, entrega aquele valor com done: false, e congela tudo ali — variáveis locais incluídas — até o próximo .next(). É lazy: o trabalho só acontece quando alguém puxa.

A2. for...of é açúcar pro protocolo

for (const n of contador()) {
  console.log(n);   // 1, 2   — o `return 99` NÃO entra no for...of
}

O for...of chama .next() em loop e para quando done fica true. O value do passo final (o return) é ignorado pelo for...of — ele só existe pra quem chama .next() na mão ou usa yield*.

A3. yield vai nos dois sentidos

Isto quase ninguém sabe: .next(x) passa x de volta pra dentro do generator — é o valor que a expressão yield assume quando retoma. 

function* dialogo() {
  const nome = yield "qual seu nome?";
  const idade = yield `oi ${nome}, qual sua idade?`;
  return `${nome} tem ${idade} anos`;
}

const d = dialogo();
console.log(d.next().value);        // "qual seu nome?"
console.log(d.next("Ana").value);   // "oi Ana, qual sua idade?"
console.log(d.next(30).value);      // "Ana tem 30 anos"

O primeiro .next() não tem pra quem entregar valor (o generator ainda não parou em nenhum yield), por isso o argumento dele é sempre descartado.

A4. yield* delega pra outro iterável

function* letras() { yield "a"; yield "b"; }
function* tudo() {
  yield 1;
  yield* letras();   // "desenrola" o outro generator aqui
  yield 2;
}
[...tudo()];   // [1, "a", "b", 2]

A5. Async generator = tudo isso + await

async function* pode usar await no corpo. .next() agora devolve uma Promise<{ value, done }>, e você consome com for await...of. O resto do modelo é idêntico: lazy, pausa no yield, congela o estado local. 

async function* paginado(): AsyncGenerator<number> {
  let pagina = 1;
  while (true) {
    const dados = await buscarPagina(pagina);   // simula fetch
    if (dados.length === 0) return;             // acabou → encerra o iterável
    for (const item of dados) yield item;       // entrega um a um
    pagina++;
  }
}

for await (const item of paginado()) {
  console.log(item);   // consome sem nunca ter a lista inteira na memória
}
Este é o caso de uso nº 1 fora de streaming: paginação. APIs devolvem 100 resultados por página; um async generator te deixa escrever for await (const x of todosOsResultados()) e esconde o "busca próxima página quando acabar". SDKs de LLM fazem exatamente isso pra listar modelos, arquivos, batches.

O que acontece no momento em que voce chama gen() (um generator)?

C. Chamar o generator só cria o objeto iterador. Nenhuma linha do corpo executa até o primeiro .next() (ou a primeira volta de um for...of / for await...of). É por isso que generators servem pra sequências infinitas e pra trabalho caro sob demanda.

Prática A (15 min) — pratice-04a.ts

Objetivo: sentir a preguiça (laziness) e a paginação.

  1. Sequência infinita. function* naturais() — let n = 1, while (true) { yield n++; }. Consuma com um for...of que dá break depois de 5 valores. Imprima cada um. (Prova de que while(true) não trava: só roda o que você puxa.)
  2. Página falsa. async function buscarPagina(p: number): await 100 ms; se p > 3 retorne []; senão retorne [p*10, p*10+1, p*10+2] (3 itens).
  3. Async generator de paginação. async function* todos() no molde do A5: loop de páginas, yield item a item, return quando a página vier vazia.

Parte B — AbortController a fundo

B1. Um controller, um signal, muitas operações

new AbortController() te dá dois lados: controller.signal (você passa pra operações) e controller.abort(reason?) (você chama pra cancelar). O mesmo signal pode ir pra várias chamadas — um abort() cancela todas. 

const ac = new AbortController();

const tudo = Promise.all([
  fetch("/a", { signal: ac.signal }),
  fetch("/b", { signal: ac.signal }),
  fetch("/c", { signal: ac.signal }),
]);

ac.abort();   // as três requisições são canceladas de uma vez

B2. O que o signal te oferece

Membro Pra quê
signal.abortedboolean — já foi cancelado?
signal.reasono valor passado em abort(reason) (default: um AbortError)
signal.throwIfAborted()lança reason se já cancelou — pra checar dentro do seu loop
signal.addEventListener("abort", fn)roda fn no momento do cancelamento (fechar arquivo, limpar timer)
async function trabalhoLongo(signal: AbortSignal) {
  for (let i = 0; i < 1000; i++) {
    signal.throwIfAborted();               // aborta cedo se pediram
    await passoCaro(i);
  }
}

B3. Helpers modernos — menos código

// timeout puro, sem setTimeout manual:
const res = await fetch(url, { signal: AbortSignal.timeout(5000) });

// combinar: cancela se o usuário clicar OU se estourar 5s
const doUsuario = new AbortController();
const res2 = await fetch(url, {
  signal: AbortSignal.any([doUsuario.signal, AbortSignal.timeout(5000)]),
});

AbortSignal.timeout(ms) e AbortSignal.any(signals) são nativos em Node 18+ e navegadores atuais. Na Lição 3 a gente montou o timeout na mão pra ver a mecânica; em código real, prefira AbortSignal.timeout. (MDN: AbortSignal.timeout)

B4. Distinguir "cancelei" de "deu erro"

try {
  await fetch(url, { signal: AbortSignal.timeout(3000) });
} catch (err) {
  if (err instanceof Error && err.name === "AbortError") {
    console.log("cancelado (timeout ou usuário)");
  } else {
    throw err;   // erro de verdade — repropaga
  }
}

Um abort por timeout chega como err.name === "TimeoutError" em runtimes novos; um abort() manual sem reason chega como "AbortError". Trate os dois como "cancelamento", não como falha.

Voce passou o mesmo signal para tres fetch e chamou abort() uma vez. O que ocorre?

A. O signal é um canal de broadcast. Qualquer número de operações pode escutá-lo, e um abort() dispara o evento pra todas ao mesmo tempo. É assim que você cancela um lote inteiro de chamadas com uma linha.

Prática B (15 min) — pratice-04b.ts

Objetivo: cancelar seu próprio loop e distinguir cancelamento de erro.

  1. Trabalho cancelável. async function contarDevagar(signal: AbortSignal): loop de i = 0 a 9; a cada volta signal.throwIfAborted(), depois await 200 ms, depois console.log("passo", i).
  2. Dispare e cancele. Numa async function main(): crie um AbortController, chame contarDevagar(ac.signal) sem await imediato (guarde a promise), agende setTimeout(() => ac.abort(), 850), e então await a promise dentro de try/catch.
  3. No catch: se err.name for "AbortError", imprima "cancelado no meio"; senão throw err.
  4. Versão timeout. Repita, mas em vez do AbortController manual use AbortSignal.timeout(850). Observe que o err.name agora pode ser "TimeoutError" — ajuste o catch pra aceitar os dois.
